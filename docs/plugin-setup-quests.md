# Plugin-owned setup quests

A setup quest is a **pre-workspace declaration**, not a plugin executable or a
workspace's setup wizard. Setup for a reviewed integration happens in two
quests, each rendered and executed by Ori's bounded host primitives:

1. **The install quest** is generated by Ori for each reviewed integration. It
   installs and verifies the plugin, with separate install/replacement and
   enable reviews, then hands off to the plugin's own quest.
2. **The plugin quest** is declared by the installed plugin. Its launch view
   has two screens: build or reuse the canonical group/Home, then create or
   import a workspace through the shared creator.

The template's existing `setup_wizard` continues **after a workspace exists**.
Project files, staffing, operating mode, permissions and exact-project live
verification keep their existing owners and confirmations. Asking about live
control belongs to that wizard, not to the quest. Putting workspace creation
inside `setup_wizard` would make setup depend on the workspace it must create.

## Shapes

Every quest has one compiled **shape**, inferred from its ordered step kinds.
There is no field to author:

| Shape | Ordered step kinds | Who may declare it |
| --- | --- | --- |
| `integration_install` | `integration_install`, `summary` | Generated by Ori from the reviewed-integration registry. Never authored. |
| `project_setup` | `project_connect`, `workspace_setup`, `assistant_program_staffing`, `summary` | Plugins that require `setup_quests_v2`, and user-owned templates. |
| `account_link` | `workspace_create`, `account_connect`, `account_link`, `summary` | Ori's embedded host quests, such as Email Ops. |

The former five-step shape, which began with `integration_install`, is
retired. A five-step declaration is rejected with an error naming
`setup_quests_v2` and the four-step order.

## The install quest

Ori generates one install quest per reviewed-integration registry entry. For
REAPER it is `install_ori_reaper`, titled **Install Ori REAPER Plugin**:

1. **Install Ori REAPER Plugin** uses the existing reviewed-integration reads
   and actions: review, install or replace, enable, and check again.
2. **REAPER plugin ready** shows the installed plugin and version. It offers
   **Continue: <plugin quest title>** as the primary action whenever the
   installed plugin lists a quest for this integration, and **Open Plugins**
   always. Continue opens the plugin quest in the same modal and leaves the
   install quest ready.

The catalog lists an install quest only while its plugin is **not** installed.
Its routes still resolve afterwards, so saved progress and deep links keep
working. It uses the host-quest route family:
`/?setup=quest&source=host&quest=install_ori_reaper`.

The accepted assistant's setup action is an alias. It resolves to the install
quest while the plugin is not installed, or while the installed plugin lists no
quest for the integration. Otherwise it resolves to the plugin quest. Home's
specialist card follows whichever quest the alias resolves.

## One saved setup, multiple entry points

- **Plugins → Available integrations → Guided Setup** opens the install quest
  for a reviewed integration that is not installed yet. The section is hidden
  when every reviewed integration is installed.
- **Plugins → Guided Setup** on an installed plugin opens the plugin's quest.
- **Create Workspace → select its template → Open Guided Setup** opens the same
  quest. Merely selecting a template does not start it, and ordinary template
  creation remains available.
- **Templates → select a template → Open Guided Setup** shows its quest title,
  description and ownership, then opens the same saved setup. Plugin templates
  and quest declarations are read-only; user-owned templates retain their normal
  editors. Loading/failure/missing-quest states remove the launch link, and a
  failed catalog read can be retried without blocking the template library.
- The accepted assistant's setup action is the alias described above. None of
  the other entry points requires an accepted assistant offer or creates one.

User-owned templates have a separate blank authoring flow under **Templates →
select a user template → Setup quest**. It edits only bounded display copy for
the same four fixed ordered steps and selects one host-reviewed integration.
The quest is listed only while that integration's plugin is installed. See
[User-owned setup quests](user-setup-quests.md).

Catalog discovery performs reads only. Opening a quest may create an inert
progress row; it does not install/enable anything, build a group, create a
workspace, start an application, or grant access. Confirmed consequences still
use the existing revision checks, review receipts and idempotent owner adapters.

Routes are compiled by Ori:

```text
GET  /api/setup-quests
GET  /api/setup-quests/{pluginID}/{questID}
GET  /api/setup-quests/{pluginID}/{questID}/runs/{runID}
POST /api/setup-quests/{pluginID}/{questID}/open | /dismiss | /children | /restart
POST /api/setup-quests/{pluginID}/{questID}/runs/{runID}/open | /dismiss
POST /api/setup-quests/{pluginID}/{questID}/runs/{runID}/actions/{actionID}
GET  /api/user-template-setup-quests/{templateID}/{attachmentID}
```

The scoped roots use the same HTTP methods and bounded request bodies as the
assistant alias. The former `runs/{runID}/preparation` route is removed. IDs in
a path select installed data only. Current-user identity comes from the host;
bodies cannot select an owner, plugin, quest, source, adapter or permission
scope. Discovery returns `plugin_id`, `id`, title/description, qualified
`template_id`, `ownership` and, for install quests only, `integration_key`. It
never returns a plugin-authored route or executor.

## Authoring contract

In `.ori-plugin/plugin.json`:

- Include `setup_quests_v2` in `requires_host_features`, retaining other
  required features. `setup_quests_v1` is no longer a supported feature, so a
  manifest that still requires it is refused like any unknown feature, and a
  host without v2 refuses a v2 manifest.
- Add `setup_quests`, at most eight declarations. Each uses a stable unique ID,
  plain display copy and exactly the four `project_setup` steps in order. There
  is no install step: the install quest owns installation.
- `workspace_launch` is required and contains exactly `group_title` and
  `group_name`. The former runtime title and instructions are unknown fields.
- Each quest names one blueprint contributed by this same plugin and the
  expected assistant-program ID. That blueprint's manifest must explicitly set
  `"setup_quest": "<quest-id>"`, contain the matching assistant program, and
  declare project connection support. Foreign, missing or orphaned references
  reject resolution.

The declarative schemas are
[`setup-quest-v2.schema.json`](../internal/plugin/schema/setup-quest-v2.schema.json)
and
[`workspace-surface-v1.schema.json`](../internal/plugin/schema/workspace-surface-v1.schema.json).
The Go normalizer additionally enforces serialized byte limits, plain text and
cross-document ownership. Unknown fields—including commands, URLs, routes,
adapters and `owner_plugin_id`—are rejected. No template reference can import a
quest from another plugin.

Discovery and execution are restricted to **host-reviewed integrations**. The
installed owner's integration key, blueprint and program must match its reviewed
registry entry. Installing an arbitrary marketplace contribution with a quest
block does not add an executor or enter the reviewed catalog. An installed
plugin whose manifest is invalid or still requires `setup_quests_v1` lists no
quest for that integration, and the alias falls back to the install quest.

## The integration precondition

Every `project_setup` root and child reads the integration before any step. The
read uses the same reviewed-integration adapter and checks as the install
quest.

- **Integration ready.** The installed plugin ID and version are recorded on
  the root, and the steps read normally.
- **Integration not ready.** Every step is blocked with the integration's
  reason, such as `integration_disabled` or `integration_not_installed`. The
  lifecycle is `needs_attention`, and the projection carries a `precondition`
  with the reason, guidance, integration receipt and install quest ID.

The modal then shows one panel titled **The integration needs attention**,
with the guidance, the integration receipt rows and one **Open install quest**
button. Nothing else is clickable. The precondition never changes the plugin
and never counts as a step.

## The launch view

A `project_setup` quest with `workspace_launch` opens on two screens, labelled
"Step N of 2" under the description "Create your group, then create a
workspace.":

1. **`group_title`** is complete when the Home exists, or when the group policy
   is `none`. It is always enabled.
2. **Create New Workspace** is complete when the project step is complete and a
   project receipt exists. It is enabled once the group is complete, or at once
   when the group policy is `recommended` or `none`.

The preparation gate is removed. There is no preparation screen, no
`acknowledge_preparation` action and no preparation check. Once the workspace
exists, the existing **Team and extras** view and the workspace open action
work as before.

## REAPER release and the reviewed pin

REAPER **0.6.0** is the first release that declares its quest under
`setup_quests_v2`: `reaper_setup` version 2 with four steps, group-only launch
copy and blueprint version 7. Installed v0.5.1 and v0.5.2 plugins require the
retired `setup_quests_v1`, so this host refuses their manifests until they
update. The earlier pinned v0.5.0 declared no quest: it installed, and its
install quest offered only **Open Plugins**.

The reviewed pin now points at the published v0.6.0 release, so the install
quest hands off into the plugin's four-step quest once the plugin is installed,
enabled and verified. An existing installation from the official unpinned Git
URL is offered **Review verified replacement** first; nothing rewrites an
installed plugin without that confirmation. The pin's verification evidence and
the procedure for moving it again live in
[REAPER integration](reaper-integration.md). A local demo can still use
`scripts/reaper-demo.sh` with a development source.

## Progress, reset and Start over

Progress is keyed by current user plus exact quest identity: host install quest,
plugin quest or user-template attachment. It is not an assistant relationship,
and a host install root never adopts a plugin, user or assistant root. Roots
created under the retired assistant-slug identity are no longer reachable.

A child inherits the shared integration/Home identity, **not** its parent's
project folder, selected mode, team or permissions. Canonical owners still
derive all readiness.

When a saved root's declaration version cannot be read by the current
declaration, the quest is **incompatible**. The modal shows the existing
guidance sentence, the explanation "Your group, project and team stay. Only
your setup progress is reset.", and a primary **Start over** button. There is no
confirmation dialog. Opening or dismissing the modal leaves the incompatible
record unchanged.

Start over calls `POST .../restart` on the assistant alias, plugin-quest or
host-quest root. It deletes that root, its children and their review and
operation receipts in one transaction, then reads a fresh root. Groups,
projects, teams, plugins and user-template bindings are untouched, so steps
they satisfy read as complete again. The fresh root's `first_completed_at`
history starts over. User-template quests have no restart route; remove and
recreate the quest instead.

## Host-owned setup quests

Ori can also ship a setup quest for one of its **built-in** templates. The
first is **Set up Email Ops** (`email_ops_setup`), which takes a user from the
goal "set up email" to a linked, readable mailbox. Host quests are compiled
into Ori from `internal/hostquests/`. No plugin, template file, or request
can add, replace, or edit one. The full contract is in
[Host-owned setup quests](architecture/host-setup-quests.md).

Embedded host quests use the `account_link` shape from the table above. The
generated install quests share the host-quest routes but not the embedded
catalog.

The Email Ops steps are:

1. **Review your Email Ops team** opens the shared Workspace creator on its
   Team step. The Inbox role is staffed and locked, because mail access is
   granted to the agent named Inbox. The step completes when an Email Ops
   workspace exists; the quest never creates one itself.
2. **Connect Gmail** reads the Google connection. Settings opens in a new tab
   and **Check again** re-reads it. The quest never starts OAuth.
3. **Link the mailbox** is a reviewed consequence. The review names the
   workspace and account; confirming links the connection's existing Gmail
   credential with read and search only, through the same linker as the
   workspace's own **Connect email** action.
4. **Email Ops is ready** offers the workspace, and inbox triage only when a
   system model can run. Triage is always a separate task the user starts.

Entry points all open the same saved progress:

- The assistant's **Email** capability shows **Set up email** while email is
  not set up and no Email Ops workspace exists. Available and revoked email
  keep their existing actions.
- **Templates → Email Ops → Open Guided Setup**, labelled "Ori built-in ·
  read-only."
- **Create Workspace → Email Ops → Open Guided Setup**.
- The link `/?setup=quest&source=host&quest=email_ops_setup`.
- A quiet **Resume** card in Home's Quests flyout while the quest is started,
  unfinished, not dismissed, and never completed. **Not now** records the
  quest's dismissal, and opening the quest again clears it. Closing the quest
  window only hides it, so an unfinished quest can be resumed from the card.

Routes mirror the plugin family without `children`, and add one read that
never creates progress:

```text
GET  /api/host-setup-quests/{questID}
GET  /api/host-setup-quests/{questID}/status
GET  /api/host-setup-quests/{questID}/runs/{runID}
POST /api/host-setup-quests/{questID}/open | /dismiss | /restart
POST /api/host-setup-quests/{questID}/runs/{runID}/open | /dismiss
POST /api/host-setup-quests/{questID}/runs/{runID}/actions/{actionID}
```

The catalog lists host quests with `source: "host"` and `ownership: "host"`.
A built-in template names its quest with `setup_quest`, and the match needs
both sides, so neither the template nor the quest can claim the other alone.

### Why plugins cannot declare account-link quests

Plugin and user-template validators require the `project_setup` shape. A plugin
or user declaration that uses the account-link kinds is rejected:

- **The consequences are host-reviewed.** Connecting an account and linking a
  mailbox touch credentials and a vault. Those adapters exist only for Ori's
  own readiness owner, and a declaration cannot point them at another account,
  vault, or workspace.
- **Older hosts fail closed.** A plugin that needs a different shape needs a
  new host feature flag first, the way `setup_quests_v2` replaced
  `setup_quests_v1`.

```bash
go test ./internal/plugin ./internal/projecttemplates ./internal/setupjourney ./internal/setupjourneyhttp ./internal/specialist ./internal/reviewedintegration
go test ./internal/hostquests ./internal/server -run 'EmailOps|HostQuest|SetupJourney|GoldenRouteTable'

scripts/e2e.sh --workers=1 tests/install-quest.spec.ts tests/plugin-setup-quests.spec.ts tests/email-setup-quest.spec.ts
```

Browser tests mock consequence endpoints and exercise desktop/mobile discovery
from Plugins, the picker and Templates, the install quest handoff, the
precondition panel, Start over, shared progress, existing-group reuse,
read-only plugin editors and catalog failure/retry. They do not install plugins
or access/control REAPER. Full Go tests, ratcheted lint and scoped security
checks remain the repository's delivery gates.
