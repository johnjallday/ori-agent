## Findings-first path inspection (task 1.2; read-only)

## Record and state contract (task 1.3)

**Ownership and storage.** The new library is one Home-owned, schema-versioned managed document indexed by `(owner_user_id, station_workspace_id, normalized AssistantProgramKey)`; use a lock + atomic replacement in Ori-managed storage (not inside source folders or an ordinary Home directory reference). Its persistent marker on the exact Home switches that Home's portfolio **metadata authority** from the legacy Home `Portfolio.Projects` to the library, only on an explicit reviewed library initialization, never on GET, login, provider reinstall, or Home restart. On initialization, copy the existing explicitly edited linked-project fields with their exact `(link_id, project_workspace_id)`, revision and source into library entries once under a migration receipt. The old Home portfolio values/operation receipts remain an immutable compatibility/history snapshot; all subsequent old and new UI/API edits route through one library service. Legacy direct service writes must delegate or fail closed on initialized Homes, not silently diverge. An uninitialized Home continues using the existing portfolio service unchanged; incomplete initialization must fail closed or reconcile by the recorded input digest before the pointer is published. Revalidate the Home/link on every association; never change Home or link provenance, role bindings or project-private state. The store is inaccessible to generic Home file tools. Coordinate explicit Home trash/restore/removal with the store marker, preserving history as appropriate and blocking writes while absent. Implementation in 2.2/2.7 must test the crash points and old API compatibility before exposing it.

**Records (no browser-selected paths).** All IDs are random opaque stable values scoped by the document owner/Home key, not display names, positional indexes or mutable path hashes. JSON decoding refuses unknown fields and invalid sizes. Each record carries a schema version and `revision` for compare-and-swap; document write revision serializes cross-record changes. Timestamps are UTC and labeled by source, never used to infer a production stage.

## Consent, threat and race contract (task 1.4)

**Distinct consequences:** a native-picker selection is a short-lived reference, not a durable grant; connecting a discovery root is reviewed Home-scoped metadata-only consent, optionally with *one* explicitly disclosed bounded scan. Each subsequent rescan/narrower follow-up is its own explicit action. Connecting one exact child via the canonical project creator is a new reviewed consequence, with File-only as default and staffing separate. An agent's proposal is inert and cannot scan, issue tokens, accept reviews, call creator/commit, or access source files. File-only use requires neither REAPER running nor a model. The browser can send only server-issued root/catalog/link IDs, relative scope IDs from known records and bounded metadata strings, never a typed absolute/relative filesystem path.

## v1 service, API and UI contract (task 1.6)

**Service/files:** `internal/projectlibrary/{model,store,roots,discovery,query,reviews,activation,studio_sessions}.go` owns pure Home-scoped operations over narrow workspace/provider/root/creator interfaces; it does not import HTTP or chat handlers. `internal/server/assistant_library.go` constructs trusted picker, provider, storage, scan and creator adapters. `internal/sessionhttp/{assistant_library,assistant_studio_sessions}.go` validates current user, strict request JSON and Home/role/provider policy through the shared application service. `internal/chathttp/workspace_portfolio_tools.go` exposes only bounded reads and inert proposals from the same service; wire both chat and task factories, with checks repeated at call time. `internal/web/static/js/modules/{project-library,studio-session-panel}.js`, existing `workspace-assistant.tmpl` and `assistant-program.css` integrate into the Home. Any final filename change requires updating the task checklist/docs before coding.

**Eligibility and states:** an exact owner/provider/program Home can hold the library whether or not REAPER is installed or a model is configured. Offer Add folder and explicit adopt-linked-projects on a Music Home (not a generic unrelated Home); a single-project intake may associate a verified exact link with that existing Home but never creates/adopts a same-named Home implicitly. Only recognizable project-folder evidence creates an entry; ambiguous `.rpp` alternatives form one entry with choices. Known unsupported DAW markers (Ableton/Logic) can enter the catalog; eligible REAPER activation needs installed compatible REAPER, an approved active root or separately proven picker/project authority, a supported `.rpp` choice and canonical owner check. A catalog-only record is **not** an Assistant Project Link. Production stage enum `unknown | idea | writing | recording | editing | mixing | mastering`; administrative status enum `unknown | planning | active | on_hold | complete | archived`. `unknown` is the unset state, not a user-editable claim of progress. Priority is an optional 0–5 user choice (unset distinct from 0); `next_action` bounded text and existing portfolio dates/milestones/blockers/deliverables/archive-review keep their old meanings. File mtime is labeled `observed_file_modified_at`, scan time is `scanned_at`, Home user edit time is `updated_at`, accepted session time is separate; none is labeled “last worked on” without an authoritative source. `connected`, `catalog_only`, `available`, `revoked`, `provider_unavailable`, `live_ready` have distinct sources and timestamps; no REAPER-active claim based on opening a file.

**API shape (under existing workspace/Home prefix):** `GET /api/workspaces/{workspaceID}/assistant-program/library` (paged query and root/coverage summary), `GET .../library/{entryID}` (bounded detail), `POST .../library/initialize/{review,commit}` (one-time old-field copy + explicit exact-link adoption), `POST .../library/roots/{pick,review,commit}` (picker has empty body; review shows exact root/scope, commit may include *one* scan), `POST .../library/roots/{rootID}/scans/{review,commit}` (explicit follow-up/rescan), `POST .../library/roots/{rootID}/revoke/{review,commit}`, `POST .../library/{entryID}/fields/{review,commit}`, `POST .../library/{entryID}/activation/{review,commit}` plus bounded per-entry queue receipt APIs; `GET/POST .../library/{entryID}/sessions` and `POST .../sessions/{sessionID}/{goal,recap,share}/{review,commit}` (reviewed goal/recap/share), `GET .../library/resume`. Each POST requires strict JSON (reject unknown fields, duplicate/trailing JSON, oversized payload), owner/Home and action-specific revision checks; review responses disclose effects/expiry, commits require explicit `confirm`/review token and idempotency key, never a GET side effect.
