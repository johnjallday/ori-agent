# File Curator guidance

File Janitor works without an agent or a provider key. Its optional File Curator
explains filing choices, important-original backup considerations, and the limits
of Undo and stored protection evidence. It cannot approve filing, operate backups,
fetch credentials or grant access.

## Availability and identity

Open **File Janitor → Settings → Curator** to see built-in guidance availability.
Ori associates guidance with the installed capability's actual companion agent
instance—not its display name, entry-agent position or a skill named
`file-janitor`. Renaming a Curator, reusing an agent definition, or assigning
another lead does not change this boundary. Other attachments of a shared agent
do not acquire guidance automatically.

Trusted template creation records the actual seeded instance. Older workspaces
are repaired only when saved built-in role evidence is unambiguous. Otherwise,
choose the intended existing agent explicitly or use **Add a Curator**. A stale
or ambiguous association is not guessed from an agent's name. Removing the
attachment or capability removes its host context, including from cached runtime
resolution.

## Bundled content, not imported-skill trust

The installed binary embeds
`internal/filecuratorguidance/skills/file-janitor/SKILL.md`; the repository's
`.agents/skills/file-janitor/SKILL.md` is a parity-tested mirror. A checkout or
file-based skill discovery is unnecessary at runtime.

Host guidance remains separate from selectable user skills. Toolbox selection,
MCP availability and task skill overrides cannot replace it. Existing user
instructions and imported-skill trust settings are preserved. No shared agent
definition, tool allowlist or opt-in setting is modified to attach guidance.

## Stored facts and review return

The approved File Janitor folder's projection is shared by the review UI and the
associated Curator in chat/tasks, including non-entry and CLI paths. Reads use
Ori-owned settings/workspace metadata and the existing saved backup scope. Paths
stay server-side. Root identity, grants, scope and association are revalidated
before late facts can be published. Unavailable roots retain generic advice, not
old folder facts; stored evidence is not a live filesystem permission check.

[Backup & Recovery](backup-and-recovery.md#optional-protection-advice-while-filing)
describes optional dismissal, navigation, return limits and fresh filing approval.
Generic adopted-folder eligibility and entry-agent protection remain unchanged.

## Validation limits

Automated coverage includes installed-style embedding without a checkout,
captured provider requests, owner/association/root lifecycle tests, bounded
browser state, and isolated Chromium filing/creation/return journeys. Invented
stored coverage and unknown/unavailable presentation fixtures prove contracts,
not an actual backup or restore. No live backup provider or paid model call is
required by these tests. Human screen-reader use and other browser engines are
not claimed by the Chromium checks.
