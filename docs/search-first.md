# Search one folder on this Mac

On a new local Mac installation, open Ori in the browser. Choose **Documents**, **Downloads**, or **Choose another folder…** to make a folder searchable. For Documents or Downloads, Ori asks for confirmation by folder name before indexing. Choose **Allow search** to continue, or **Cancel** to leave your sources unchanged. This is separate from macOS privacy permissions: macOS may also ask for access, but won’t necessarily prompt if access was already decided. Choosing your first folder also makes Files your starting page on a new installation. **Not now** goes to Home without confirming a workspace directory or completing Welcome. Canceling a folder dialog makes no choice at all.

If you've already set up Ori, use **Files** in the rail beside Home's workspace cockpit. The rail has two destinations, **Files** and **Map**, and there is no separate Tree toggle: Files is the tree, and it is where searchable folders are managed. Visiting Files or **Map** does not change your starting page; the button beside the Files heading does: **Make Files my starting page**, or **Start on Map instead** once it is. If the choice was changed in another window meanwhile, Ori says so instead of overwriting it. When Files is your starting page and a workspace exists, Ori opens Files in Home. Once any workspace exists, the address `/search` opens Files too; before then it is the first-run page above. If setup is incomplete, that page offers **Start or resume workspace setup** instead of promising a map, and it is still where its folders are managed. Once you're in Files, filename search runs locally: querying or selecting a folder never calls a model and doesn't require a Personal HQ.

## Search Files by name

Files has one box, **Search by name…**. Type part of a name: Ori finds workspaces, notes, tickets, chats, agents and stored files whose _names_ match, in every workspace, even ones you have not opened, and shows them in a **Results** tab beside the tree. On this Mac it also lists files from folders you made searchable, merged newest first with the rest and labelled with their folder. The tree is never narrowed by a search; **Show in tree** on a result opens its parents and focuses its row. Matching is by name only, ignores case, and never reads note text, ticket bodies or file contents. Results arrive 25 per kind with **More results**. If one kind could not be searched, the others still show and that kind says so with **Retry**.

Press **/** to focus the box, **Down** to walk the results, **Enter** to open one and **Esc** to clear. A file from a searchable folder is selected first; **Enter** again opens it in its reader and **Shift+Enter** reveals it in Finder. These are explicit desktop actions.

To search in one place only, open a row's menu and choose **Search in this workspace** (a group row says **Search in this group**) or, on a folder inside Files or Outputs, **Search in this folder**. A searchable linked folder, and a search-only folder, offer the same. A chip beside the box reads `in <name>`; its ✕ takes it off and searches everywhere again. A workspace or group scope finds every kind inside it; a folder inside a workspace finds only files in that folder; a searchable linked or search-only folder asks only the filename index for that folder. Esc clears the term but leaves the chip. **Search _folder_ in Files** on a workspace page, on a creation receipt or on an Explore card opens Files with that chip already in place, in the same tab; nothing about the folder goes in the address.

The term is sent in a request body for each search and nowhere else. It is not in the address, browser storage, the remembered tree tabs, a log, or a request URL, and a result in a search-only folder is never stored as a tab. Away from the Mac that runs Ori, Files searches what is inside workspaces and says in one line that folders you made searchable are not searched here.

## Create a workspace from a folder after workspace setup

On this Mac, choose **New workspace from folder…** at the foot of Files' tree, then Downloads, Documents or **Choose another folder…**. The review opens right there: keep the folder name or give the workspace its own name, choose whether to make filenames searchable, then select **Create workspace**; Files then shows the new workspace's folder. There’s no template, model or agent to choose. The assistant’s **Explore a folder** offers the same card in the conversation. The new workspace has no agents. Choose **Add an agent…** to hire a manager for the verified folder or assign an existing agent. For example, **Hire a Downloads Manager…** opens an editable name, brief and model. **Hire only** adds the agent to this workspace without starting work. To get setup suggestions, select **Start a first-look ticket after hiring**, then **Hire & look around**. An already-assigned agent can do the same from **Folder first look → Look around**. This opens one ticket to review folder names and structure, not file contents. Reopening the workspace shows progress or the saved report; applying any suggested setup is a separate decision. Neither choice creates another workspace or enables filename search. Opening or cancelling the form doesn't assign anyone. **New Workspace** still offers advanced setup and uses the same folder selection and consent checks. Linking lets workspace tools read the original folder in place; **filename search** is a separate choice. It indexes names, locations and dates on this Mac, not file contents. Choosing or cancelling a folder does not create anything. Search consent does not hire an agent, send files to a model, start Filing or prepare Notes.

If the folder already has a verified workspace, **Open** it without creating another one or connecting filename search. Choose a workspace if more than one links to that folder. An older link may ask you to verify its current folder because its original disk identity was not recorded. If the folder is searchable but has no workspace, it is in the **Search-only folders** group (below); its **Connect to workspace** keeps its existing index. Nothing is converted on upgrade. If creation succeeds but the search connection fails, keep the workspace and choose the same folder again in Files to finish just that step.

## Searchable folders in Files

On this Mac, each folder a workspace links to says after its name, in Files, whether it is searchable: **Searchable**, **Indexing…**, **Partly indexed**, **Folder unavailable**, **Needs verifying** or **Not searchable**. A dot repeats it in a shape of its own (filled, half, struck, dashed, hollow); when the row is too narrow for the words, the dot stays and the words are its tooltip. Ori reads the list once each time you open Files; if it cannot be read, the rows say the status is unavailable rather than "Not searchable". Away from the Mac that runs Ori, rows say nothing about search.

A linked folder's menu starts with its status: the state, how many filenames are indexed and when it was last indexed, and why an index is partial. Below it are the actions that apply:

- **Make searchable** asks first, naming the folder, in the same words as the first-run page: Ori will index filenames, locations and dates in this folder on your Mac, won’t read file contents and won’t give agents access. **Cancel** changes nothing. An older link whose folder identity was not recorded asks you to confirm it is the folder the workspace links to; until you do, the row reads **Needs verifying** for the rest of that visit to Files. If the folder is already searchable through another workspace, Ori says so instead.
- **Refresh index** maps the folder again. The row reads **Indexing…** while it does, then says how it went. A folder that can only be partly read reads **Partly indexed** and says why; one that is not there reads **Folder unavailable**: reconnect the original folder and refresh, or remove it and choose another.
- **Remove from search** asks first, then clears only that folder's filename index. The workspace, its link to the folder, its notes, tickets and files all stay, and so does the folder itself. Its files leave any results on screen. Nothing grants search again by itself: not a refresh, a return from Map or a restart.
- **Search in this folder** scopes the search box to it.

Searchable folders that no workspace links to are listed in a **Search-only folders** group at the foot of the tree, when there is at least one. Their rows do not open. Their menu offers **Search in this folder**, **Connect to workspace** (the same review as above; the folder then moves under that workspace's Linked folders with its index kept), **Refresh index** and **Remove from search**. Another tab's change shows here as soon as Files hears of it.

A searchable folder alone is not a workspace or permission for an agent to read files. Ori indexes names, relative locations, modification dates and local identity metadata. It doesn't extract text, move files, hand their names to a model, or store your queries in note-search history. Directory access is limited to the selected local APFS folder. Private Ori roots, system folders, whole volumes and overlapping sources are refused. System privacy controls can still refuse a selection.

- When two names match, use the folder, relative parent and date to tell them apart. Notes and headings are a separate scope in the search palette.
- **Enter** requests the displayed reader for a supported document or media file; **Shift+Enter** requests Finder. Unsupported files offer Reveal rather than a launch association. These are explicit desktop actions, not permission for an agent to read the file. A moved, replaced or inaccessible result can no longer be opened from the old row.
- **Partly indexed** means some entries couldn't be mapped, not that there are no more files. Hidden/tooling directories, app bundles, symlinks, other mounts and flagged cloud placeholders are excluded. There are caps on traversal time, depth, entries and index size.
- There is no watcher. Files shows the saved index; use **Refresh index** to map again. Refresh starts a new generation, so deleted or previously indexed files aren't counted as newly verified.
- Unlinking a workspace does not revoke an independent search grant: the folder moves to Search-only folders. Resetting ordinary workspace setup does not create or revoke grants; deleting app records clears all search sources and results. Start Fresh resets the starting page as well.

Before setup is done, the first-run page lists its folders under **Manage search locations** with the same Refresh and Remove from search, and **Add folder…** in its sidebar.

The implementation uses fixed system document readers, not “your default app.” Files in Home keeps a short-lived descriptor per tab in memory on this Mac, not a history of searches: the term, the scope, the selected result and how many pages of each kind were loaded. Switching Files → Map → Files in a tab keeps the search as it was. Leaving the page and coming **Back** brings it back, asked again, so a result that has since been renamed or removed is simply not there; a scope whose workspace or folder is gone brings back nothing rather than the same term in the wrong place. **Search _folder_ in Files** uses the same descriptor to arrive with its folder. Terms, names and paths do not travel in links, browser storage or the map's view state. New tabs start independently; don't rely on restoration across a reload, timeout or restart. Away from the local Mac there is no descriptor and the term is simply cleared on leaving.

The headless demo disables all desktop effects; it cannot verify Finder, a reader, or an OS privacy prompt. Native acceptance requires a separate foreground Mac test account with synthetic files.
